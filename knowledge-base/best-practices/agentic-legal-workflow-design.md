# Agentic Legal Workflow Design

This knowledge base entry describes how to compose the skills in this repository into multi-step, agentic workflows — where an AI system plans, executes, and iterates across several skills with human review gates between steps — without losing attorney supervision, privilege protection, or defensibility. It is a design reference, not a skill. Skills in `skills/operations/`, `skills/admin/`, and `skills/customer-service/` should cross-reference this document whenever they describe how their output flows into the next step.

## Why this matters in 2026

Coverage across Bloomberg Law, ABA Law Practice Magazine (March/April 2026), Wolters Kluwer's *Future Ready Lawyer 2026* study, and Legora's *Year of Agents in Legal AI* analysis converges on the same observation: legal AI is moving from single-task prompting to orchestrated agent workflows in which multiple specialized steps run in sequence, each grounded in matter context and firm playbooks. Gartner projects that 40% of enterprise applications will embed task-specific AI agents by the end of 2026, up from under 5% at the start of 2025.

For legal teams, this shift raises two hard problems that a naive agent loop does not solve on its own:

1. **Supervision and defensibility.** An attorney of record is accountable for every decision made in the attorney's name. An agent that chains multiple steps without human gates converts a reviewable decision into an opaque series of actions.
2. **Privilege and work product boundaries.** An agent that moves documents between tools, writes intermediate artifacts to shared storage, or invokes consumer-grade AI for any step may erode privilege or create discoverable work product. The framework in `ai-privilege-and-work-product.md` applies to every link in the chain, not just the first one.

The guidance below is designed to let a firm adopt agentic workflows without giving up either.

## Core design principles

**Skill-as-step.** Treat each skill in this repository as a single, auditable step in a larger workflow. A skill has a defined input contract, a defined output contract, and a disclaimer that it is AI-assisted and requires attorney review. Chaining skills means chaining those contracts — never skipping the disclaimers or the review gates.

**Human review gates are mandatory between phases, not between every step.** A design that puts a human gate between every step reduces the workflow to a sequence of manual prompts and captures no leverage. A design that removes all gates forfeits defensibility. The right pattern is a small number of phase boundaries — typically intake, analysis, drafting, and review — with a human gate at each boundary and full traceability within each phase.

**Matter context is a first-class input to every step.** Every skill already accepts matter context as part of its `Required Input`. In an agent workflow, that context is carried forward from the first skill to the last, including the matter ID, the client identity, the governing jurisdiction, any protective order and Rule 502(d) order status, the applicable playbook, and the privilege posture. The orchestrator is responsible for ensuring this context is passed through every step without alteration.

**Playbook grounding beats prompt cleverness.** The Contract Clause Analyzer, NDA Triage, and Legal Response Templates skills all accept a configured playbook. An agent workflow should prefer playbook-configurable skills over one-off prompts, because the playbook is the durable, firm-specific artifact that makes the output defensible across matters.

**No tool changes without logging.** Whenever the agent switches from one AI tool to another, or from an enterprise AI to a non-enterprise AI, the switch must be logged with the reason. This is the single most important discipline for preserving privilege posture across a multi-step workflow.

**Public reference architecture (May 2026 — `anthropics/claude-for-legal`).** On May 12, 2026, Anthropic released `anthropics/claude-for-legal` (Apache-2.0) — a 12-plugin, 80+ skill, 20+ MCP-connector public reference architecture for legal Claude plugins covering commercial, corporate, employment, privacy, product, regulatory, AI-governance, IP, and litigation practice areas, plus law-student, legal-clinic, and Builder-Hub plugins. The release crystallises a vocabulary that maps onto this repo's existing skill design and is worth recording for cross-team communication and convergence-or-divergence tracking. (i) *Practice profile via cold-start interview.* Each plugin ships with a `cold-start-interview` skill that runs a 10–20 minute guided intake against seed documents (signed contracts, internal playbook, escalation matrix, prior memos) and writes a personalised `CLAUDE.md` practice profile that every other skill in the plugin reads at runtime. The practice-profile pattern corresponds to this repo's `config.yml` Firm Config Keys block (and the per-skill `Firm Config Keys Used` register) — same intent (write practice context once, read it everywhere), realised in a parallel-but-compatible format. (ii) *Matter-workspace skill pattern.* Every plugin includes a `matter-workspace` skill plus matter-lifecycle helpers (`matter-intake`, `matter-update`, `matter-briefing`, `matter-close`, `portfolio-status`). The pattern corresponds to this repo's matter-context-as-first-class-input design principle and the cross-skill matter file framing in `admin/client-intake-summary`, `admin/document-intake-extractor`, and the operations-skill `Required Input` blocks. (iii) *Citation guardrails — source-attributed vs. `[verify]` tag.* The reference architecture distinguishes citations originating from research-connector tools (CourtListener, Trellis, Descrybe, Solve Intelligence) — which carry a source attribution — from citations originating from model knowledge — which carry an explicit `[verify]` tag. When no research tool is connected, a reviewer-facing note above the deliverable records that sources were not verified. The pattern corresponds to this repo's `ai-citation-verifier` GREEN/YELLOW/RED labeling and the ungrounded-tool default-label-raise rule; the reference architecture's `[verify]` tag and the repo's RED-by-default-for-ungrounded rule are two surface forms of the same risk-tier mechanism. (iv) *Legal Builder Hub trust layer.* The `legal-builder-hub` plugin curates community-contributed skills behind a trust layer: hidden-content scan, prompt-injection detection, SHA-pinned updates, license gates (personal / firm-internal / product-embedding), freshness gates on bundled reference content, re-scan at update, and an install log. The QA framework scores incoming skills against a Legal Skill Design Framework (nine design parameters, three legal failure modes, a trust-surface check). The Trust-layer pattern corresponds to this repo's eval-framework + non-overridable `firm.ethics.*` config keys + the skills/README.md SKILL.md-format requirements — same intent (gate skills entering the catalog on safety, freshness, and license-compatibility), realised through repo-internal review rather than an installed trust runtime. (v) *Managed-agent cookbooks.* Five managed-agent cookbooks (`diligence-grid`, `docket-watcher`, `launch-radar`, `reg-monitor`, `renewal-watcher`) deploy scheduled background work through the Claude Managed Agents API rather than as interactive plugins; each cookbook = `agent.yaml` + depth-1 subagents + steering examples; deployment script resolves file references, uploads skills, creates leaf-worker subagents, and POSTs the orchestrator to `/v1/agents`. The cookbook pattern is the architectural model for any future scheduled-agent extensions of this repo (e.g., a docket-watcher counterpart to the litigation skill set, a renewal-watcher counterpart to the transactional skill set) and indicates that orchestrator-tool-scope linting (`lint-tool-scope.py`) and cookbook dry-runs (`test-cookbooks.sh`) are part of the public reference pipeline. (vi) *Subagent delegation as Research Preview.* Single-level subagent delegation (one orchestrator → one tier of leaf workers, no deeper recursion) is the current Research Preview constraint on the public reference architecture. The constraint matches the four-phase pattern below: phase boundaries hold the human gate; within a phase, leaf workers can be invoked in parallel without further recursion. (vii) *Microsoft 365 surface.* Contract-touching skills in the reference architecture are explicitly authored for the Word sidebar with tracked-changes output; tabular skills (tabular-review, claim-chart, entity-compliance, renewal-tracker) produce multi-sheet xlsx. The repo's `contract-clause-analyzer`, `discovery-response-drafter`, `deposition-prep-outline`, and `legal-research-memo` skills should be assumed to encounter the same surface in firm deployments and should not assume a chat-only output channel. The reference-architecture release confirms that the design principles above are not idiosyncratic to this repo — they are the converged form of the legal-AI agent-design conversation as of May 2026, and the repo's litigation- and firm-practice-side framing extends rather than diverges from that converged form.

**Open evaluation benchmark for legal agents (2026 — `harveyai/harvey-labs` LAB).** Harvey's open-source Legal Agent Benchmark (LAB), released May 6, 2026, supplies a 1,200+ task, 24-practice-area, 75,000+ expert-rubric-criteria evaluation harness that is structurally compatible with the repo's eval framework. LAB tasks follow a fixed shape: an instruction, a client matter file containing relevant materials (some of which are deliberately distractors), and a requirement that the agent produce a reviewable work-product (a deal-team memo, an issues list, a research analysis) judged against expert-written rubric criteria. The task shape mirrors the design contract this repo's skills already honour (defined `Required Input`, defined `Output Format`, defined `Output Requirements`, and an attorney-reviewable deliverable). LAB is a candidate external eval surface for any skill in this repo whose practice-area scope overlaps with the LAB practice taxonomy (the corporate-side matter-workspace and diligence patterns most directly), and the LAB task shape is a candidate template for next-cycle eval-rubric extensions where the repo's internal eval framework needs an out-of-distribution stress test.

**LAB initial leaderboard (May 26, 2026 — Harvey AI blog and Artificial Analysis partnership).** Harvey published the first baseline results twenty days after the May 6 LAB launch — closing the pending publication-watch entry the prior monitor cycle carried — and confirmed an ongoing partnership with Artificial Analysis to maintain a regularly-refreshed leaderboard as new frontier models ship. Under LAB's strict all-pass standard, frontier models complete fewer than 10% of tasks end-to-end in aggregate. The initial baseline reported in Harvey's "Legal Agent Benchmark Initial Results" post: Claude Opus 4.7 (~7.1%), Claude Sonnet 4.6 (~5.4%), Claude Opus 4.6 (~4.2%), GPT-5.5 (~2.1%), and Gemini 3.5 Flash (~0.8%). Reaching the top of the leaderboard runs to roughly $50 per task and over 20 minutes of latency. The leaderboard shifts substantially across the 24 practice areas — Harvey's "jagged intelligence" framing — and no single model leads every one. Three operational implications for this KB: (i) The under-10% aggregate end-to-end completion rate empirically confirms that the four-phase human-gate-at-phase-boundaries pattern remains the right design — releasing skill output without an attorney-of-record review under a strict all-pass standard exposes the firm to the same defect-rate Harvey's frontier baseline reports, and the LAB completion rate is the single best public number a firm technology committee can use to calibrate review-intensity expectations for legal-agent output. (ii) The cost-and-latency floor at the top of the leaderboard (~$50/task, >20 min) sets the practical ceiling for any "agent-replaces-attorney-review" claim in the near term: a firm that is paying that floor for the best-available top-of-leaderboard model is buying a less-than-10% all-pass completion rate, which is not a substitute for the institutional second-verifier the `pre-filing-independent-review` skill operationalizes. (iii) The practice-area variance ("no single model leads every one") indicates that a multi-model orchestrator routing different phases to different models by practice area is a candidate next-cycle architectural pattern for matter-workspace-style skills — and that the model-selection decision is now itself a matter-context input (alongside jurisdiction, privilege posture, and protective-order status) that the orchestrator must record at intake and carry through every phase. The Artificial Analysis partnership means the leaderboard becomes an ongoing tracking surface; the next-cycle question is whether published practice-area-by-practice-area cuts make it possible to map specific repo skills to specific LAB practice areas for a routine external-eval pass. This KB treats the leaderboard as a calibration signal for review-intensity defaults, not as a guarantee of any specific firm's deployment quality — the LAB numbers measure frontier-model task-completion on Harvey's curated tasks, not the quality of any particular firm's verification pipeline.

**The scaffold, not the model name, is the unit of legal-AI performance (June 2026 — Legal Nodes scaffold study and the LegalOn 2026 Contract Review Benchmark).** Two empirical artifacts published the same day (June 22, 2026, both reported by Artificial Lawyer) supply the missing complement to the LAB leaderboard above: where LAB measures *model* end-to-end completion rates, these two measure how much the *scaffold* — the skill, playbook, retrieval, verification, and guardrail layer wrapped around the model — changes the result for a fixed model. (i) The Legal Nodes scaffold study (Legal Nodes consultancy, with MikeOSS) held the base model constant (Claude Opus 4.8) and ran it on legal tasks under several different scaffolds; the same model scored materially differently depending on the scaffold around it, and a leaner open-scaffold setup (MikeOSS) reached comparable quality at a fraction of the cost. The study's headline conclusion — that model-only evaluation gives an incomplete picture of legal-AI performance, because output quality depends on the base model *and* the scaffold around it — is the empirical case for this repo's entire premise: a skill file is a scaffold, and the value a skill adds is precisely the model-independent delta the study isolates. (ii) The LegalOn 2026 Contract Review Benchmark (Daniel Lewis, CEO; 11 models across 3,282 head-to-head reviews against 21 precision-critical guidelines) found that general-purpose models *"identified the right topic but missed the legal standard"* — the defect mode the **Playbook grounding beats prompt cleverness** principle above and the Protégé *process knowledge* component exist to close, since the legal standard (the controlling test, the clause-risk taxonomy, the jurisdiction-specific certification rule) is encoded in the scaffold's playbook, not recoverable from the base model's general competence. The benchmark also reported that a costlier frontier model did not necessarily win on legal work (Anthropic's Fable 5 cost more than twice Opus 4.8 without beating it on contract drafting reliability), reinforcing that scaffold investment dominates raw model-upgrade spend for legal output quality. Four implications for this KB, all strictly additive. (a) *Read the LAB leaderboard as a model-only floor, not a deployment estimate.* The under-10% aggregate completion figure recorded above measures models without firm scaffolds; the scaffold study shows the deployed number for a well-scaffolded skill is a different — and model-independent — quantity, so a firm technology committee should evaluate the *model+scaffold pair* it will actually run, never a model-name leaderboard alone. (b) *The eval-framework discipline is two-sided.* The repo's internal eval should hold the scaffold constant when comparing models and hold the model constant when comparing skill versions, and must not attribute to the model a quality delta the scaffold contributed (or vice versa); the "right topic, missed the standard" finding is the canonical example of a defect a model swap will not fix and a playbook revision will. (c) *Playbook grounding is now empirically, not just doctrinally, load-bearing.* The benchmark gives the **Playbook grounding beats prompt cleverness** principle a citable evidentiary basis for client and malpractice-carrier conversations: the measured gap between "right topic" and "right legal standard" is the gap the firm's configured playbook closes. (d) *Cost framing.* When a firm weighs a frontier-model upgrade against scaffold investment, the June 2026 evidence points toward the scaffold: a leaner model under a better scaffold matched a more expensive setup in the scaffold study, and a more expensive model under the same conditions did not beat a cheaper one in the contract-review benchmark. This KB treats both artifacts as calibration evidence for the scaffold-centric design stance the repo already takes, not as endorsements of any specific vendor or model; the numbers measure curated-task performance, not any particular firm's verification pipeline.

**Open-source multi-agent legal reference architecture (May 2026 — `AnttiHero/lavern`).** Lavern v0.15.0 (released May 16, 2026; announced via Artificial Lawyer on May 20, 2026) is the first published Apache-2.0 multi-agent legal system that wires a debate-and-verification orchestrator over a frontier LLM (Anthropic Claude, Mistral, or local Ollama) and that publishes the orchestration discipline as its primary contribution rather than the prompts. The repo packages 67 specialist agent prompts (59 specialists, 7 workflow-specific orchestrators, 1 base orchestrator), 21 MCP tools (debate, scoring, verification, grounding, memory, knowledge base, quality checks), 9 workflow templates from single-specialist counsel to full adversarial review, and 5 seeded legal datasets (CUAD, MAUD, ACORD, UNFAIR-ToS, LEDGAR). The architecture maps onto five design primitives that extend — rather than duplicate — the patterns already in this KB. (i) *Evidence-cite-required debate protocol.* Every agent finding must cite specific text from the parsed document; challenges must cite counter-text; findings without citations are not admitted to the debate board. The repo's `pre-filing-independent-review` chain-of-custody audit and the `ai-citation-verifier` GREEN/YELLOW/RED labeling enforce the same evidence-citation discipline on the human-attorney side; the Lavern primitive is the orchestrator-side equivalent that gates which model outputs are even allowed to enter the workflow's finding register. (ii) *Three-layer verification with a 10-pass pipeline.* Evaluator gate (drops weak findings) → adversarial debate (red team / blue team) → 10-pass verification pipeline that runs each finding through `context`, `ux`, `clarity`, `structure`, `accuracy`, `completeness`, `risk`, `formatting`, `legal_design`, and `delivery` passes, each failing closed independently. The 10-pass taxonomy is a richer formalization of the four-category error sweep (citations / quotations / characterizations / statutory text) in `ai-hallucination-sanctions-2026.md` Expanded Defect Taxonomy and is a candidate template for next-cycle extensions of the verification queue inside `ai-citation-verifier` and the four-category error sweep inside `pre-filing-independent-review`. (iii) *Precedent Board with tentative→confirmed promotion.* Persistent memory across engagements: a new pattern enters as `tentative` and is promoted to `confirmed` only after it recurs across documents with consistent verdicts; stale patterns decay. This is a candidate template for a future playbook-evolution mechanism in the repo's Contract Clause Analyzer, NDA Triage, and Legal Response Templates playbooks — where a firm-specific pattern emerging from a sequence of matters can be promoted from `tentative` to `confirmed` only after enough recurrence to retire the risk that the pattern was an artifact of one matter's facts. (iv) *Human gates with explicit confidence scores and grounding indicators.* Each engagement delivery includes a weighted confidence score (across findings, debate resolutions, verification checks, and evaluator scores), a grounding indicator showing how well the evidence is rooted in the source document, and an audit trail of debate resolutions. The pattern operationalizes this KB's phase-gate model with quantitative signals the reviewing attorney can read at a glance; the repo's existing skill outputs should be assumed to evolve toward carrying analogous confidence and grounding indicators in next-cycle iterations. (v) *Toggleable jurisdiction-of-inference and air-gapped local mode.* Setting `LAVERN_PROVIDER=mistral` routes the orchestrator, agents, debate, verification, briefing analyser, partner consult, and Clawern processing through Mistral in Paris instead of Anthropic in the US; setting it to `local` routes the entire pipeline through Ollama. This is the first published legal-AI reference architecture in this scan's record with a fully toggleable EU-jurisdiction inference path and a fully local air-gapped option as first-class deployment modes, and it supplies a vocabulary the repo's `ai-privilege-and-work-product.md` and `ai-governance-legal.md` documents may need to adopt as EU clients, GDPR-bound matters, and high-confidentiality matters become more common in firm workflows. The Lavern README is explicit that the orchestration-quality claim is a hypothesis rather than a settled result ("we have internal evaluation; we don't have a public benchmark"); this KB treats Lavern as a reference architecture for design vocabulary, not as a validated quality benchmark — the open-empirical-question framing is itself a model for how this repo's verification-extension claims should be presented to firm technology committees.

**Enterprise vendor vocabulary alignment (2026).** LexisNexis's May 2026 expansion of Protégé — its agentic legal-AI platform layer — introduced a design vocabulary that maps onto the principles above and is worth adopting as shared terminology when communicating with clients and firm technology committees. In the Protégé framing, a *skill* is a packaged, reusable capability defined by three components: (1) *process knowledge* — the legal playbook, decision criteria, and escalation paths specific to the matter type (e.g., the contract-clause risk taxonomy, the privilege-review decision tree, the FRCP-26(g) certification standard); (2) *context resources* — templates, clause libraries, policy excerpts, and secondary authority the agent draws on at runtime (e.g., the firm's standard NDA playbook, the jurisdiction-specific standing-order index, the citation-verifier GREEN/YELLOW/RED framework); and (3) *operational guardrails* — the explicit boundary conditions governing what the agent must not do and which decisions require human approval before execution (e.g., `firm.ethics.no_ai_as_verifier`, `firm.ethics.truthful_ai_disclosure_on_direct_inquiry`, the FRCP-26(g) overobjection guardrail). The Protégé framing also foregrounds two gate-discipline principles that reinforce the phase-boundary model above: *visible task decomposition* (the agent presents a step-by-step execution plan before acting, so the supervising attorney can halt the workflow before a bad step runs) and *matter-scoped memory* (the agent's learned context is bounded to the current matter by default; cross-matter learning requires an explicit opt-in, ensuring that confidential information from one client's matter cannot bleed into the operational context for an unrelated client). Both principles are already implicit in this repo's "Skill-as-step," "Human review gates," and "No tool changes without logging" design principles; the vendor vocabulary makes them explicit in a form that translates directly into language clients, auditors, and malpractice carriers recognise. For skills in this repo, "process knowledge" corresponds to the skill's `Purpose`, `Limitations`, and non-overridable `firm.ethics.*` config keys; "context resources" corresponds to `Required Input`, `Optional Configuration`, and `Firm Config Keys Used`; and "operational guardrails" corresponds to the `ESCALATE` call, the `Release-to-File` attestation gate, and the hard rules in `Output Requirements`.

**The connector substrate is standardizing on MCP (May–June 2026) — and the tool boundary is now a named, permission-aware interface.** Two of the repo's load-bearing design principles — *No tool changes without logging* and *Preserve privilege at tool boundaries* (orchestrator responsibility #5) — assume a "tool boundary" that, until recently, was an ad-hoc per-vendor integration. Over a roughly thirty-day window that boundary acquired a common standard. The Model Context Protocol (MCP) — the open AI-to-system integration standard originated by Anthropic, in which an *MCP server* exposes a system's data and actions and an *MCP client* (the AI application) consumes them — is consolidating as the cross-vendor interoperability layer for legal work, and the two dominant legal document-management vendors shipped server-side support within days of each other: iManage launched its MCP server on May 14, 2026, and NetDocuments announced its Legal Context Graph and `ndConnect` MCP interface the same day (May 14, 2026), exposing a continuously-mapped, permission-governed view of matters, documents, and communications to external AI tools (Claude, ChatGPT, and others) *while preserving each firm's existing permissions and ethical walls at the server*. In parallel, Microsoft's Legal Agent for Word reached enterprise general availability on May 3, 2026 (announced April 30) with MCP integration into both iManage and NetDocuments, giving a Word-embedded agent authenticated access to privileged documents and firm work product. The June 2, 2026 Artificial Lawyer essay "MCP: The Standard that Decides Legal AI's Future" (Liam Reid, Legatics) reframes the shift from a plumbing question into a *procurement and positioning* question — the two gaps it names (the *context gap*: the AI cannot see the rest of the matter; and the *action gap*: the AI cannot write back into the systems where work happens) are exactly the gaps the four-phase orchestration pattern below depends on closing without a human acting as the manual bridge between systems. Three implications for this KB, all of which sharpen existing principles rather than introduce a new one. (i) *The tool whitelist becomes a connector-standard question.* Orchestrator responsibility #5 ("confirm the destination is covered by the firm's privilege-preserving tool whitelist before the move") can now be expressed as "is the destination MCP server inside the firm's ethical-wall and permission model, and does it preserve those controls server-side?" — a more concrete, auditable test than a vendor-by-vendor whitelist, because the permission-aware DMS servers (NetDocuments's permission-governed graph; iManage's security model) enforce the wall at the connector rather than relying on the orchestrator to remember it. (ii) *Authenticated agent access to privileged content raises, not lowers, the logging bar.* A Word-embedded or DMS-connected agent with authenticated read/write access to privileged work product is precisely the configuration `ai-privilege-and-work-product.md` treats as highest-risk; the standardization makes the access easier to grant, so the "No tool changes without logging" discipline and the per-step run log (orchestrator responsibility #3) must record which MCP server was touched, under which user's permissions, on every step — the connector standard does not relax the audit-trail requirement, it makes a uniform audit trail finally feasible. (iii) *MCP-readiness is now a matter-context and procurement input.* Whether a firm's DMS, transaction-management, and review platforms are MCP-enabled determines which phases of the four-phase pattern can run as connected agent steps versus manual copy-paste bridges; like model selection (the LAB practice-area-routing point above), connector availability is a deployment fact the orchestrator should record at intake. This KB treats MCP as the converging substrate for the tool-boundary principles already stated here, not as a new principle — but the convergence is worth tracking, and the privilege-at-the-connector and authenticated-agent-access points are candidate additions to `ai-privilege-and-work-product.md` if a firm deployment surfaces a concrete ethical-wall-at-MCP-server question.

**Deploying skill files without Claude Code — the no-MCP / hosted-project deployment pattern (July 2026 — `veronica-builds/claude-for-legal-web`).** Every reference architecture recorded above (the `anthropics/claude-for-legal` plugin suite, the Lavern multi-agent system, the MCP connector wave) assumes a Claude Code / MCP-server / scheduled-managed-agent runtime. Most firms adopting this repo's skills will not have that runtime; they will paste a skill's markdown into a hosted project workspace (a Claude Project, a ChatGPT custom GPT, or an equivalent instructions-plus-uploaded-files surface) with no slash commands, no MCP connectors, and no scheduler. A community adaptation surfaced this cycle — a port of the `anthropics/claude-for-legal` practice-area workflows to hosted Claude Projects (six practice areas: commercial, privacy, employment, litigation, IP, AI-governance), which is derivative content but articulates a coherent no-runtime deployment discipline directly applicable to this repo's own cross-assistant, markdown-skill-plus-`config.yml` model. The concepts below are extracted and re-expressed in this repo's terminology; they are strictly additive design guidance for the hosted-project deployment case and change no skill file. (i) *Guardrails belong in the always-active instruction layer, never only in on-demand retrieved files.* A hosted workspace splits into two tiers: an always-active custom-instruction/system layer, and a retrieved knowledge layer surfaced only when the conversation matches it. Retrieval is probabilistic — a skill file may not surface for a given prompt. Therefore every guardrail that must fire on *every* output — the privilege legend, the `ATTORNEY REVIEW REQUIRED` / Release-to-File attestation gate, the `[[VERIFY]]` marker discipline, the `ESCALATE` triggers, and this repo's non-overridable `firm.ethics.*` rules — must live in the always-active layer, not be left to the retrieved skill file alone. This maps directly onto how the repo already separates its non-overridable hard-rule blocks (which must never be missed) from a skill's ordinary body content, and gives a concrete deployment rule for it: hard rules go in the workspace instructions; the rest of the skill can be a retrieved file. (ii) *File names are retrieval signals.* In a hosted project, the assistant uses the uploaded file's name as a retrieval cue, so skill files should keep descriptive, workflow-named filenames (a `contract-clause-analyzer.md` surfaces on a contract-review prompt; a generically-named `reference.md` will not). The repo's existing category-and-skill-name filenames already satisfy this; the deployment note is not to rename them on upload. (iii) *One workspace per practice area, not one firm-wide workspace.* Always-active instructions degrade as they try to cover more domains at once; a single workspace carrying every practice area's playbook, triggers, and escalation rules dilutes retrieval quality across all of them. Deploy the repo's skills grouped by practice area (roughly, its `operations` / `admin` / `customer-service` / `sales` grouping) into separate workspaces rather than one monolith. (iv) *Replace scheduled-agent skills with human-in-the-loop upload workflows.* The scheduled managed-agent cookbooks in the `claude-for-legal` reference architecture (docket-watcher, renewal-watcher, leave-tracker analogues) have no counterpart in a hosted project with no scheduler and no external connectors. The deployment substitute is a standing human step: a recurring calendar reminder, a person who exports the relevant data (contract list, docket sheet, leave register) and uploads it, and a fixed trigger phrase that runs the analysis. This is the manual-bridge form of the four-phase pattern's phase boundaries and is the correct fallback whenever the *action gap* and *context gap* named in the MCP entry above cannot be closed by a connector. (v) *A pre-production deployment verification checklist.* Before attorneys use a hosted-project deployment on live matters, run a fixed acceptance sweep: a trigger test (each skill's entry phrase loads the right workflow and executes it step-by-step, not as a summary), a guardrail test (a planted red-flag clause is classified correctly and returns `ATTORNEY REVIEW REQUIRED`), a `[[VERIFY]]`-marker test (a jurisdiction-specific threshold question returns the marker), a limitation test (a request to pull from a system the workspace cannot reach returns the standard "cannot access — please upload" statement rather than a fabricated result), a privilege test (the privilege legend appears verbatim), an escalation test (a planted escalation scenario halts and routes to the named contact), and an attorney-review-gate test (every complete deliverable ends with the review attestation). This is the deployment-time counterpart to the repo's `evals/` framework — where the eval framework grades a skill's design in the abstract, this checklist verifies that a *specific hosted deployment* of the skill still fires its guardrails after the markdown has been transplanted out of Claude Code. This KB treats the hosted-project pattern as a deployment-surface reference for the repo's non-Claude-Code users, parallel to the Microsoft-365-Word-sidebar surface note in the `claude-for-legal` entry above; it is calibration guidance for how the same skill files behave on a retrieval-plus-instructions surface, not a new skill or a new guardrail.

**The all-pass gap — why high per-item accuracy still yields an unusable deliverable (July 7, 2026 — the independent LAB-AA leaderboard).** The LAB entries above recorded the benchmark's launch (May 6) and Harvey's own initial baseline (May 26), and left open a tracking question: what happens when an independent party re-implements LAB and publishes a standing leaderboard. That happened on July 7, 2026, when Artificial Analysis published **Harvey LAB-AA**, its own implementation of the Legal Agent Benchmark — 120 private legal tasks across the 24 LAB practice areas (corporate M&A, capital markets, tax, litigation, bankruptcy, and others), each task consisting of an instruction plus a matter file of reference documents, each deliverable graded against a rubric of atomic binary pass/fail criteria, with results refreshed as new models ship. The publication closes the recorded re-evaluation trigger on `harveyai/harvey-labs`. Four findings, and five design consequences for this repo — all strictly additive, none changing an existing principle.

*The findings.* (1) **Two metrics, not one.** LAB-AA reports both a *criterion pass rate* (the share of individual rubric items a deliverable satisfies) and an *all-pass rate* (the share of tasks where **every** criterion in the rubric passes — no partial credit). (2) **The gap between them is enormous.** The leading model at launch reached a criterion pass rate above 93% but an all-pass rate of only 14.2%; the next tier of models clustered around 7.5% all-pass; 13 of the 28 models evaluated at launch fully completed **zero** tasks. Even the leader leaves roughly 86% of professional legal deliverables incomplete by the benchmark's standard. (3) **Cost and completion are decoupled.** Cost per task spanned roughly three orders of magnitude across the evaluated field, and a substantially cheaper model matched a frontier model's all-pass rate at a small fraction of the cost — while the cheapest models bought very low criterion pass rates. (4) **The leaders run long agentic loops.** Top performers averaged on the order of 60 turns and 15–25 minutes per task, and completion correlated with how much work the model actually did per task rather than with a single well-formed prompt.

*The consequences.* (i) **Attorney review cannot be sampled — this is now an empirical finding, not just a doctrinal preference.** A legal deliverable is an all-pass artifact: it fails if *any single* atomic element is wrong — one fabricated citation, one wrong deadline, one wrong dollar figure, one inverted severity rating. The 93%-criterion / 14%-all-pass gap is the quantitative statement of exactly that asymmetry: a model can be right about nearly everything and still hand the attorney a deliverable that is not filing-ready. This is the strongest available public number in support of the **Drafting gate: no exceptions** standard in *Review-gate discipline* below, and of the `Release-to-File` attestation in `pre-filing-independent-review` — a percentage-sampling review of AI-produced work product is structurally the wrong instrument, because the defects that matter are exactly the ones a sample misses. (ii) **The rubric-atomization taxonomy is a richer error taxonomy than the repo's four-category sweep.** LAB rubrics decompose a deliverable into the atoms a reviewing stakeholder would scrutinise — facts, conclusions, citations, severity ratings, recommendations, deadlines, dollar amounts, and formatting/deliverable-form requirements. The repo's existing four-category error sweep (citations / quotations / characterizations / statutory text, in `pre-filing-independent-review` and `ai-hallucination-sanctions-2026.md`) covers the *authority* atoms well and the *operative-detail* atoms not at all: dates, deadlines, dollar amounts, severity and risk ratings, party names, and whether the deliverable actually produced every element the instruction asked for are outside its four categories. **Actioned this cycle** — `pre-filing-independent-review` v1.2 adds a fifth sweep category (Category E — operative details and deliverable completeness) covering precisely these atoms. The same extension is a candidate next-cycle addition to `contract-clause-analyzer` (severity-rating verification) and `demand-letter-drafter` / `discovery-response-drafter` (date and amount verification). (iii) **Published leaderboard numbers are a scaffold-stripped floor, not a deployment estimate.** The independent implementation deliberately *removed* the vendor's custom tools and document-generation skill scripts in order to measure raw model ability, and ran the models through its own agent harness. That is the cleanest possible confirmation of the scaffold entry above: the published number measures a model *without* a legal scaffold, which is precisely the layer a skill file supplies. A firm reading 14.2% as "what AI can do on legal work" is reading a floor produced by stripping away the thing this repo exists to provide. The corollary is a caution in the other direction: the scaffold delta is what a firm must *demonstrate*, not assume. (iv) **The harness is part of the measurement — treat any single leaderboard as one implementation's result.** Independent re-implementations of the same benchmark, differing in agent harness, judge model, file-name matching strictness, and tool availability, produce materially different rankings of the same models. When a firm technology committee cites a leaderboard, the correct unit is *benchmark + implementation + model + scaffold*, and a model-selection decision defended by a leaderboard rank alone is not defensible. (v) **Long agentic loops are a logging obligation, not just a cost.** If a competent legal-agent run takes on the order of sixty tool-calling turns, then orchestrator responsibility #3 (*Log every step*) is describing an audit trail of sixty-odd loggable actions per deliverable, not five. Any firm claiming a defensible AI audit trail should confirm that its per-step run log actually captures agent-internal turns and not merely the phase boundaries a human sees. This KB treats LAB-AA as a calibration signal for review-intensity and audit-trail defaults; the numbers measure frontier-model performance on curated tasks under one harness, and say nothing directly about the quality of any particular firm's scaffolded, human-gated pipeline.

**Legal sycophancy and the elicitation paradox — why consultation quality drops precisely when a client most needs the lawyer to lead (July 2026 — DLawBench).** A multi-institution academic benchmark published June 11, 2026 (arXiv 2606.13931, "DLawBench: Evaluating LLMs Through Multi-Turn Legal Consultation") tests models not on single-shot drafting but on the thing this repo's intake- and client-facing skills actually do: hold a multi-turn conversation with a client, decide what to ask versus when to write the memo, and produce a deliverable that is checked against a hidden ground-truth record the client never sees. Twenty-six models were evaluated across four simulated client-interaction styles built from two independent behavioral axes (how forthcoming the client is, and how much the client defers to the lawyer's lead) rather than from a single cooperative/difficult spectrum. The finding is directly relevant to every skill in this repo that intakes a client's own account of the facts, and it names a failure mode the repo's existing traceability rules do not yet test for.

*The finding.* (1) **Legal sycophancy is a distinct, hidden failure mode.** It is not a model agreeing with a client's stated preference (ordinary sycophancy); it is a model quietly adopting the client's own understanding of the facts and the client's own theory of the case as the working premise, then building a competent-sounding analysis on top of that premise instead of testing it against what a neutral record would show. The benchmark's diagnostic signature is a deliverable that mentions essentially all of the client's stated facts (high coverage) while resolving almost none of the disputed ones against the independent record (low resolution) — a memo can look thorough and still be wrong in exactly the way that matters. (2) **The failure concentrates in the two client styles least likely to trigger the reviewer's suspicion.** A client who argues back (the "adversarial" style) degrades model performance the least, because pushback itself signals "verify this." The styles that degrade performance most are the compliant, low-initiative ones — a client who leans on the lawyer to lead and needs reassurance, and a client who gives minimal, vague, evasive answers — precisely because the model responds to low disclosure by quietly filling the gap in the client's favor rather than asking a harder question. (3) **Coverage and resolution are separable metrics, and separating them is the point.** The benchmark deliberately scores "did the deliverable capture what the client said" separately from "did the deliverable correctly resolve what the client said against the governing record," specifically so that a model cannot earn credit for a well-organized restatement of the client's own account. Design consequences for this repo, all strictly additive.

(i) *A client-facing intake or consultation skill should treat client deference or vagueness as a signal to ask more, not a signal to infer more.* This is the opposite of the natural drafting instinct — a sparse or non-committal client answer invites the model to be helpful by filling the gap smoothly, and the benchmark shows that is exactly where quality collapses. **Actioned this cycle** — `admin/client-intake-summary` v2.3 → v2.4 adds an Elicitation-Depth Scaling rule: a vague, deferential, or "you're the expert, just handle it" answer from the prospective client lengthens the Follow-Up Checklist and widens the `[[VERIFY]]` flagging rather than narrowing it, and the skill is instructed never to read client silence on a disputed point as license to assume the point resolves in the client's favor. (ii) *The repo's existing Source-Note Traceability family of rules (client-intake-summary, document-intake-extractor, demand-letter-drafter's damages rule, legal-research-memo's holdings rule) already separates "the client/document said this" from "this is unsupported," which is the coverage half of the benchmark's distinction — but none of those rules yet test the resolution half: whether a client-supplied characterization (fault, causation, contract breach, "clearly" language) has been checked against an independent source rather than merely tagged to its origin in the client's own account. A source tag proves where a statement came from; it does not prove the statement is correct. This is a candidate next-cycle refinement across the traceability-rule family: distinguish a **client-framing tag** (this is the client's characterization, sourced but unverified) from a **verified-fact tag** (this has independent documentary or record support) at the sentence level, not only at the field level. (iii) *Candidate next-cycle extensions beyond the actioned skill:* `_shared/email-drafter` and `_shared/meeting-summarizer` both narrate a client's or a meeting participant's account of events and would benefit from the same coverage-versus-resolution separation; `customer-service/legal-response-templates` intakes a requester's own framing of a complaint (a DSAR, a negative review, a demand) as its primary input, which is structurally the exact scenario the benchmark models. None of these three skills is modified this cycle; each is flagged for the next cycle's review. (iv) *Benchmark vocabulary worth adopting for firm technology-committee conversations:* "legal sycophancy" as the named failure mode (distinct from citation hallucination, which this repo's `ai-citation-verifier` and the sanctions-docket KB already cover extensively) and the coverage-vs-resolution distinction as an audit lens a reviewing attorney can apply to any AI-drafted intake or consultation summary — not just "did it capture what I told it" but "did it independently test what I told it." This KB treats DLawBench as an academic benchmark result, not a vendor claim or a validated production deployment measure; the numbers describe model behavior on the benchmark's simulated clients, not any particular firm's intake pipeline.

## A canonical four-phase pattern for litigation matters

The following pattern is drawn from current practice at firms that have publicly described their agentic pilots (Artificial Lawyer coverage of April 2026) and is consistent with the ABA Law Practice Magazine's March/April 2026 introduction to agentic AI. It is organized around phase boundaries rather than individual steps.

**Phase 1 — Intake and framing.** Skills: `admin/client-intake-summary`, `admin/document-intake-extractor`, `operations/legal-research-memo` (issue-framing mode). Output: a structured matter record with parties, claims, governing jurisdiction, known deadlines, gaps, and an open-question list. Gate: the responsible attorney reviews and approves the matter record, sets the privilege posture, and confirms the protective-order and Rule 502(d) status before Phase 2 begins.

**Phase 2 — Analysis.** Skills: `operations/regulatory-compliance-checker`, `operations/contract-clause-analyzer`, `operations/privilege-log-reviewer` (for internal investigations), `operations/legal-research-memo` (full memo mode). Output: a set of analytical artifacts keyed to the matter record. Gate: a senior attorney reviews the analysis for substantive accuracy, flags any ESCALATE items, and authorizes drafting in Phase 3.

**Phase 3 — Drafting.** Skills: `operations/demand-letter-drafter`, `operations/discovery-response-drafter`, `operations/deposition-prep-outline`, `customer-service/legal-response-templates`. Output: court-filed or client-delivered drafts with all `[[CLIENT TO PROVIDE]]` and `[[VERIFY]]` placeholders resolved. Gate: final attorney review, client sign-off where required, and service.

**Phase 4 — Closeout and knowledge capture.** Skills: `admin/time-entry-cleaner`, `_shared/meeting-summarizer`, plus a playbook-update step (not yet a standalone skill — captured in the changelog for now). Output: clean time entries, a matter summary, and any playbook updates flowing back into the firm's configuration. Gate: billing partner sign-off on time entries and playbook-change approval by the practice group lead.

A comparable pattern for transactional and in-house workflows substitutes different skill sets — `nda-triage` at intake, `contract-clause-analyzer` in analysis, `legal-response-templates` in drafting — but preserves the same four-phase boundary structure.

## Orchestrator responsibilities

Whatever system runs the workflow — a human paralegal, an in-house workflow tool, or an agent framework — it has the same responsibilities at each phase boundary:

1. **Validate inputs before the next skill runs.** A skill with missing required input should not be invoked; the orchestrator should surface the gap to a human.
2. **Pass matter context forward unchanged.** Any change to jurisdiction, privilege posture, or protective-order status must come from an attorney instruction, not from an agent's inference.
3. **Log every step.** Each step's input, output, skill version, and reviewing attorney (where applicable) is recorded in a run log stored with the matter file. The log is the audit trail that supports both internal QC and discovery responses about the firm's AI use.
4. **Stop on ESCALATE.** Any `ESCALATE` classification anywhere in the workflow halts the agent until a human resolves it. The `nda-triage` and `privilege-log-reviewer` skills produce `ESCALATE` calls deliberately; the orchestrator must honor them.
5. **Preserve privilege at tool boundaries.** If the orchestrator must move an artifact between tools — for example, from the drafting skill to a document management system — it must confirm the destination is covered by the firm's privilege-preserving tool whitelist before the move.

## Review-gate discipline

Each phase gate has a minimum review standard. These are intentionally conservative; firms can relax them for low-stakes matters, but relaxations should be documented in the firm's AI governance policy (see `ai-governance-legal.md`).

- **Intake gate:** A licensed attorney reviews the matter record. Mandatory sign-off on jurisdiction, privilege posture, and deadlines.
- **Analysis gate:** A senior attorney reviews analytical artifacts. Mandatory sign-off on any compliance-gap findings, any privilege-log PRIVILEGED or REDACT classifications, and any regulatory-exposure findings.
- **Drafting gate:** The attorney of record reviews every draft before service or filing. Mandatory sign-off — no exceptions. This is the step that maps to FRCP 11 and its state equivalents.
- **Closeout gate:** The billing partner reviews cleaned time entries; the practice group lead approves any playbook changes flowing back from the matter.

## Failure modes to watch for

Based on the reported pilots and near-misses through April 2026, the common agentic failure modes are:

- **Silent step upgrade.** An orchestrator swaps a skill's version mid-matter without flagging the change; the output now reflects a different framework than the one approved at the intake gate. Guard: version every skill (already in the frontmatter) and log the version used at each step.
- **Context drift.** Matter context is paraphrased rather than passed through, and a jurisdictional detail quietly changes. Guard: the matter record is the single source of truth and is not rewritten by any downstream skill.
- **Privilege leak by convenience.** An agent copies a draft to a consumer AI tool for "quick cleanup," destroying the enterprise-tool chain. Guard: tool whitelist enforced by the orchestrator, not by the user.
- **Overclaim cascade.** A privilege call in Phase 2 propagates into Phase 3 drafting without a re-review. Guard: every PRIVILEGED or REDACT call has its own attorney sign-off and is not re-used without that sign-off.
- **Speed-to-served pressure.** Because the agent produced a draft fast, the responsible attorney feels comfortable compressing review time. Guard: the drafting gate's minimum review standard is absolute — no agent speed justifies skipping it.

## Notes on watch — agent-counterparty transactions

The framework above covers AI agents acting *inside* a firm's workflow, with the firm and its attorneys as the principals. A separate vector is now appearing in the public commentary: AI agents acting as counterparty proxies in transactions — placing offers, accepting offers, and binding their human principals to the terms reached. Anthropic's April 24, 2026 *Project Deal* experiment, in which 69 employees authorized AI agents to execute purchase-and-sale exchanges on their behalf and 186 deals closed at a total transaction value of just over $4,000, is the public marker for this pattern. The Legal IT Insider commentary on the experiment frames the legal-frameworks gap explicitly: contract formation, capacity, authority, and enforceability rules were not drafted with autonomous agents in mind.

This pattern is upstream of the skills in this repository — none of the skills in `operations/`, `admin/`, or `customer-service/` is designed to advise counterparties whose agents are themselves AI. But it surfaces issues that the firm should be ready to address when a client asks, when the firm itself enters an agent-mediated transaction (procurement, marketplace, or platform-routed deal), or when an agent-mediated transaction surfaces in litigation:

- **Authority and ratification.** Did the principal authorize the specific transaction or only a class of transactions? Is there a signed ratification step, and if so does it cure an out-of-scope agent action? The firm's counterparty work should not assume the answer is yes by default.
- **Formation and assent.** Whose objective manifestation of assent counts when both sides of the negotiation are AI? Click-through analogues (the National Law Review's "Who's Really Clicking 'Accept'?" framing) and the older mailbox-rule tradition both apply imperfectly. Counsel should review and document the formation theory the client is relying on before the platform launches.
- **Identity, KYC, and binding signature.** Where an agent acts on behalf of a regulated principal (broker-dealer, escrow agent, lender), the agent's identity, its authority, and its signature are open compliance items. Existing KYC and signature-block practice should be updated to address agent-mediated transactions explicitly.
- **Liability allocation.** Where an agent over-pays, under-delivers, leaks confidential terms, or is induced via prompt injection, allocation across principal, deploying organization, and tool vendor is unsettled. Standard indemnities and limitations of liability written for passive software typically do not cover the agent case.
- **Audit and traceability.** Records of prompts, decisions, and tool calls become primary evidence when an agent transaction is challenged. The orchestrator-responsibility points above (validate inputs, log every step, stop on ESCALATE) translate directly into the agent-counterparty setting; firms advising clients on agent deployments should require the same orchestration discipline of the client.

This is a notes-on-watch item, not a skill. The repo's `contract-clause-analyzer`, `nda-triage`, and `regulatory-compliance-checker` skills already carry the matter-context fields a future skill could extend; the practical near-term step is to expect counterparty AI-agent provisions in client requests for advice and to draft a firm-level take on each of the five items above before the first matter forces it.
